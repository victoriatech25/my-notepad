# ADR 0001 — 텍스트 편집 위젯 방식

- 상태: **결정됨** (P0-10 사용자 승인, 2026-10-20)
- 관련: PLAN.md §2.2, §3.6, §1.3 · 측정: [docs/measurements/phase0.md](../measurements/phase0.md) P0-03, P0-06, P0-07

## 배경
PLAN.md §2.2는 두 방식을 두고 Phase 0 측정으로 정하기로 했다.

| 방식 | 내용 |
| :--- | :--- |
| **A** | egui `TextEdit` + `String`. 커서·선택·클립보드·IME를 egui가 처리 |
| **B** | 자체 편집 위젯 + Rope(`ropey`). 보이는 줄만 레이아웃(가상 스크롤), 커서·선택·IME·Undo를 직접 구현 |

## Phase 0에서 확인한 사실
| 항목 | 결과 | 출처 |
| :--- | :--- | :--- |
| 한글 IME (Windows, MS IME) | **A에서 전 항목 통과** — 조합 위치, Enter/Space/방향키/클릭 확정, 자모 단위 Backspace, 한/영, 한자, 빠른 입력 | P0-03 |
| 입력 지연 (A) | 1MB 7.9ms · 5MB 52ms · 10MB 114ms · 50MB 738ms (약 10ms/MB) | P0-06 |
| 사용자 체감 (A) | 1MB까지 괜찮음, 그 이상 지연 체감, 10MB 이후 실질적으로 사용 곤란 | P0-06 |
| 첫 레이아웃 (A) | 1MB 0.4s · 5MB 2.3s · 10MB 5.5s | P0-06 |
| 메모리 (A) | 빈 문서 112MB(glow) → **10MB 문서 약 1.9GB** | P0-07 |
| 보이는 부분만 그리기 효과 | Markdown 미리보기 1MB: 전체 26ms → 보이는 블록만 1.4ms | P0-09 |

**해석**: A의 비용은 문서 전체를 매 입력마다 다시 배치하는 구조에서 나오며, 크기에 비례한다. 반면 IME 품질은 A가 이미 검증됐다. B는 크기 문제를 해결하지만 IME를 포함한 편집 기능 전부를 직접 구현해야 하고, **IME 품질을 처음부터 다시 검증해야** 한다.

## 결정
**단계적 하이브리드**: 편집은 A로 시작하고, 큰 파일은 별도의 가벼운 **읽기 전용 뷰어**(보이는 줄만 그림)로 연다. 큰 파일 편집(B)은 별도 단계로 앞당겨 검토한다.

| 파일 크기 | 동작 | 위젯 |
| :--- | :--- | :--- |
| ~ 1MB | 일반 편집 | A (`TextEdit`) |
| 1MB ~ 5MB | 편집 허용 + 상단 안내 "큰 파일이라 입력이 느릴 수 있습니다 · 읽기 전용으로 보기" | A |
| 5MB 초과 | **읽기 전용 뷰어**로 열기 (줄 번호, 스크롤, 선택·복사, 찾기, 인코딩 표시). "편집 모드로 열기"는 경고 후 허용 | 뷰어 (보이는 줄만 레이아웃, IME 불필요) |

- 경계값(1MB, 5MB)은 설정으로 바꿀 수 있게 하고, 첫 화면 레이아웃 시간(1MB 0.4초)을 고려해 파일을 연 직후에는 로딩 표시를 한다.
- 문서 저장소는 처음부터 `core::buffer::TextBuffer` 추상화 뒤에 둔다(PLAN.md §4.1). 뷰어와 향후 B가 같은 인터페이스를 쓴다.
- 읽기 전용 뷰어는 Phase 1에 작업 단위로 추가한다(커서 이동·선택·복사·찾기 연동 수준). B(큰 파일 편집)는 Phase 6에서 Phase 4 이후로 앞당길지 Phase 2 종료 시점에 재검토한다.

## 기각한 대안
| 대안 | 기각 이유 |
| :--- | :--- |
| A만 쓰고 큰 파일은 열기 거부 | 로그 등 큰 파일을 여는 것은 메모장 대체 프로그램의 기본 용도. 10MB에서 약 2GB 메모리는 받아들일 수 없음 |
| 지금 바로 B로 전환 | 검증된 IME 품질을 버리고 커서·선택·IME·Undo를 처음부터 구현해야 함. MVP와 UX 조기 검증 일정이 크게 늦어짐 |
| A의 레이아웃을 줄 단위 캐시로 개조 | egui `TextEdit`은 문서 전체를 하나의 배치(galley)로 다루는 구조라 내부를 고치는 것은 사실상 B를 만드는 것과 같음 |

## 결과
- MVP는 검증된 IME 품질을 유지한 채 진행한다.
- 5MB 초과 파일은 편집이 아니라 열람 중심이 된다 → 사용자에게 명확히 안내해야 한다(UX 검증 대상).
- 같은 파일이 크기에 따라 다른 위젯으로 열리므로, 찾기·인코딩·상태 표시줄 등 공통 기능은 위젯이 아니라 `core`에 둔다.

## 재검토 조건
- egui `TextEdit`이 큰 문서용 부분 레이아웃을 지원하게 되면 경계값을 다시 잰다.
- 사용자 피드백에서 "5MB 초과 파일 편집"이 자주 필요하다고 확인되면 B를 앞당긴다.
- macOS IME 검증(🍎, G0 전)에서 A가 불합격하면 이 결정 전체를 다시 연다.
