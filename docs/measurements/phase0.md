# Phase 0 측정 결과

> 측정 장비: Windows 11 PC (x86_64) · 릴리스 빌드 · eframe/egui 0.37.0 · 폰트 직접 구성(맑은 고딕 포함)
> 재현: `cargo xtask gen-samples` 후 `target/release/editor-spike.exe --perf-bench`

## P0-06 대용량 텍스트 — 방식 A (`TextEdit` + `String`)

창 없이 egui를 돌려 **레이아웃 + 테셀레이션 CPU 시간**을 잰 값이다 (GPU 그리기 제외). 입력은 문서 중간에 한글 1글자씩.

| 샘플 | 하이라이트 | 열기(읽기+UTF-8) | 첫 프레임 | 입력 프레임 평균 / 최대 | 유휴 프레임 |
| :--- | :---: | ---: | ---: | ---: | ---: |
| 1MB (1만 줄) | 끔 | 1.4 ms | 387 ms | 7.9 / 8.8 ms | 1.9 ms |
| 1MB | 켬(100개) | 1.4 ms | 390 ms | 7.9 / 8.6 ms | 1.7 ms |
| 5MB (5만 줄) | 끔 | 6.9 ms | 2.3 s | 51.8 / 53.2 ms | 11.6 ms |
| 5MB | 켬 | 6.9 ms | 2.7 s | 57.4 / 60.9 ms | 14.6 ms |
| 10MB (10만 줄) | 끔 | 18 ms | 5.5 s | 114 / 119 ms | 27.0 ms |
| 10MB | 켬 | 18 ms | 5.5 s | 128 / 137 ms | 27.6 ms |
| 50MB (50만 줄) | 끔 | 95 ms | 46.6 s | 738 / 796 ms | 178 ms |
| 50MB | 켬 | 95 ms | 40.7 s | 721 / 757 ms | 148 ms |

### 해석
- 비용은 하이라이트가 아니라 **문서 전체를 매 입력마다 다시 레이아웃하는 `TextEdit` 구조**에서 나온다 (하이라이트 켬/끔 차이 작음).
- 입력 지연은 크기에 거의 비례(약 10ms/MB): **60fps(16ms)를 지키는 한계는 약 1.5MB**, 5MB부터 체감 지연, 10MB 이상은 사실상 편집 곤란.
- 첫 레이아웃(파일을 연 뒤 첫 화면)이 1MB에서도 약 0.4초, 5MB 2초 이상 — 파일 열기 체감에 직접 영향.
- 유휴 프레임도 크기에 비례(10MB 27ms) — 커서 깜빡임·마우스 이동만으로도 CPU를 쓴다.
- **사용자 체감 (2026-10-20)**: 1MB까지 괜찮음, 그 이상은 지연 체감, 10MB 이후 실질적으로 사용 곤란 — 측정과 일치.
- 결론(잠정): PLAN.md §3.6의 "방식 A 잠정 한계 10MB"는 **성립하지 않는다.** 방식 A로 가면 편집 한계를 약 1~2MB로 낮춰야 하고, 그 이상(로그 파일 등)을 편집하려면 방식 B(자체 위젯 + 보이는 줄만 레이아웃)가 필요하다 → P0-10 ADR 0001에서 결정.

## P0-07 메모리·기동 시간 — 렌더러 × 한글 폰트 × 문서

> 재현: `cargo xtask gen-samples` 후 `cargo xtask measure --runs 10` (빈 문서 10회, 10MB 3회 평균)
> 첫 프레임: 프로세스 시작 → 첫 프레임이 화면에 나간 시점(warm). 메모리: 첫 프레임 1.5초 뒤 Windows Working Set.
> 실행 파일 크기: 13.89MB (glow + wgpu 둘 다 포함, LTO thin + strip)

| 렌더러 | 한글 폰트 | 문서 | 첫 프레임 ms 평균 (최소~최대) | 메모리 MB 평균 (최소~최대) |
| :--- | :--- | :--- | ---: | ---: |
| wgpu | 직접 구성 | 빈 문서 | 462 (416~538) | 319 (318~321) |
| wgpu | 없음 | 빈 문서 | 412 (374~510) | 318 (316~319) |
| **glow** | **직접 구성** | **빈 문서** | **362 (314~443)** | **112 (111~117)** |
| glow | 없음 | 빈 문서 | 376 (315~482) | 110 (109~111) |
| wgpu | 직접 구성 | 10MB | 5,056 | 2,153 |
| wgpu | 없음 | 10MB | 2,656 | 2,144 |
| glow | 직접 구성 | 10MB | 5,395 | 1,938 |
| glow | 없음 | 10MB | 2,517 | 1,941 |

### 해석
- **렌더러**: glow가 wgpu보다 메모리를 약 **200MB 적게** 쓴다 (112 vs 319MB). 기동 시간도 비슷하거나 조금 빠르다 → **glow 권장**.
- **한글 폰트(직접 구성)**: 메모리 영향은 약 +2MB로 거의 없다 (memory-map). 빈 문서 기동 시간 차이도 측정 오차 수준.
- **§1.3 잠정 목표 대비**: 빈 문서 메모리 ≤60MB는 glow로도 미달(112MB, 그래픽 드라이버 몫이 큼), warm 기동 ≤300ms도 미달(약 360ms). 목표 수치는 P0-10에서 측정 기반으로 재설정 필요.
- **10MB 문서 = 약 2GB 메모리**: 방식 A(`TextEdit`)는 문서 전체의 글리프 배치를 메모리에 들고 있어 크기에 비례해 폭증한다 (§1.3 목표 ≤150MB 대비 13배). P0-06의 입력 지연과 함께 **방식 B(보이는 줄만 레이아웃)가 필요하다는 강한 근거**.
- 10MB 첫 프레임이 한글 폰트 有 5초 / 無 2.5초로 차이 나는 것은 한글 글리프 레이아웃 비용(폰트 없으면 대체 문자로 처리)이다 — 방식 B에서는 보이는 부분만 배치하므로 사라질 문제.

### cold 기동 (사용자 실행, 2026-10-20)
재부팅 직후 `editor-spike.exe --renderer=glow --measure-out cold.txt`

| 구분 | 첫 프레임 |
| :--- | ---: |
| cold (재부팅 직후 첫 실행) | 416.9 ms |
| warm (바로 이어서 실행) | 241.1 ms |

§1.3 잠정 목표(cold ≤ 800ms, warm ≤ 300ms)를 이 1회 실행에서는 충족했다. 자동 반복 측정의 warm 평균(362ms)은 측정 도구가 창을 연속으로 띄우는 부하가 섞인 값이라 실제 체감보다 다소 크게 나온 것으로 본다.

## P0-08 Markdown 렌더러 비교 — A `egui_commonmark` 0.26 vs B `pulldown-cmark` 0.13 + 자체 렌더러

> 재현: `cargo xtask try md` (docs/PLAN.md를 A | B 나란히), `cargo xtask try md-block-map` (B 블록 위치표·단조성 점검)

| 항목 | A. egui_commonmark 0.26 | B. pulldown-cmark + 자체 렌더러 |
| :--- | :--- | :--- |
| egui 버전 종속 | egui 0.37 대응 버전 있음. 단 egui 업그레이드마다 이 크레이트의 대응판을 기다려야 함 | 파서(pulldown-cmark)는 egui와 무관. 렌더러는 우리 코드라 egui 업그레이드 시 직접 수정 |
| **블록 소스 줄 범위 ↔ 화면 y좌표** | **얻을 수 없음** — `show()`는 `InnerResponse<()>`만 반환하고, 내부에서만 소스 위치(offset_iter)를 씀 | **얻음** — PLAN.md 최상위 블록 98개 전부, 1MB 샘플 1,980개 전부 대응 + y·줄 모두 단조 증가 (자동 점검 통과) |
| 굵게(한글) | 실제 굵은 폰트가 아니라 색만 진하게 | (1차) bold 패밀리로 실제 굵게 → **UX-004 후: A와 같이 진한 색**, 굵은 글꼴은 옵션 |
| 제목 | Heading~Body 사이 단계 크기 + 진한 색 | (1차) 굵은 폰트 + 큰 크기 + 밑줄 → **UX-004 후: A와 같은 단계 크기·진한 색, 밑줄 없음** |
| 표 | 열 폭을 넘는 셀 내용을 잘라 표시(…) | 줄바꿈 없이 표시, 넓으면 표 영역만 가로 스크롤 (초기 버그: 셀이 첫 프레임의 좁은 폭에 맞춰 세로로 쌓임 → 수정) |
| 코드 블록·인용·목록 | 지원 | 지원 (작업 목록 ☐/☑, 번호 목록 시작 번호 반영) |
| 추가 기능 | 이미지 로더, 구문 강조 옵션, 검색 매치 색, 제목으로 스크롤 등 | 아직 없음 (이미지·각주·Front Matter·링크 동작은 Phase 3에서 구현) |
| 가상 스크롤 | `show_scrollable`에 내부 viewport 캐시 있음(위치는 비공개) | 블록 높이 표를 이미 갖고 있어 보이는 블록만 그리는 구조로 확장 가능 |

### UX-004 반영 (2026-10-20)
사용자 의견 "A가 전반적으로 나은 모습"에 따라 B 구조(블록 위치표)는 유지하고 모양만 A에 맞췄다: 제목 크기 공식(egui Heading·Body 크기 사이 단계), 굵게 = 진한 색, 블록 사이 한 줄 여백(제목 앞 추가), 글머리 = 공백 4칸 폭 안의 작은 원, 인용 = 왼쪽 3px 선 + 흐린 글자, 표 = 테두리 틀 + 줄무늬 격자 + 스크롤바 여백, 코드 = 틀 + 코드 배경색. 굵은 글꼴 사용은 화면 상단 옵션으로 비교 가능. [나란히 스크린샷](../ux/screens/p0-08-md-a-vs-b.png)

### 결론 (잠정 — 사용자 화면 비교 후 ADR 0002에서 확정)
- §3.8의 핵심 요구인 **분할 모드 양방향 스크롤 동기화·더블클릭 소스 이동**에는 블록 위치표가 필수인데, A는 공개 API로 이를 줄 수 없다 → **B 권장**.
- B는 렌더링 품질(한글 굵게·제목)도 A보다 낫고, 표 셀 줄바꿈 버그는 수정했다. 이미지·각주 등 부족한 기능은 Phase 3 범위.

## P0-09 분할 스크롤 동기화 시제품

> 재현: `cargo xtask try md` → 상단 `분할 동기화 (P0-09)`, 스크롤 측정 `md-spike.exe --scroll-bench spikes/samples/md-1mb.md`

### 동기화 방식
- 소스: 줄바꿈된 화면 행을 소스 줄 단위로 묶어 "줄 → y" 표를 만든다.
- 미리보기: B 렌더러의 블록 위치표(소스 줄 범위 ↔ y·높이). 블록 안은 줄 비율, 블록 사이(빈 줄)는 앞 블록 끝~다음 블록 시작을 선형 보간 (`sync.rs`, 단위 테스트 5개: 경계 정확, 블록 내부 비례, 빈 줄 보간, 왕복 오차 0.01줄 이내·단조 증가, 소스 줄 왕복).
- 되먹임 방지: 사용자가 움직인 쪽(기대값과 달라진 쪽, 둘 다면 마우스가 올라간 쪽)만 기준이 되고, 반대쪽에 적용한 값을 기대값으로 기억해 다시 반대로 동기화되지 않게 한다.
- 기준점: 각 화면의 맨 위.

### 미리보기 스크롤 프레임 시간 (창 없이, 폭 900px, 반 화면씩 60프레임)
| 문서 | 블록 | 전체 그리기 평균 / 최대 | 가상 스크롤 평균 / 최대 |
| :--- | ---: | ---: | ---: |
| md-1mb.md (1MB) | 1,980 | 26.0 / 59.6 ms | **1.4 / 4.8 ms** |
| md-100kb.md | 198 | 2.3 / 5.5 ms | 1.5 / 4.4 ms |

→ 1MB에서 전체 그리기는 60fps(16ms)를 못 지키지만, 블록 위치표로 보이는 블록만 그리면 충분히 여유가 있다. §1.3 "1MB 미리보기 스크롤 60fps" 목표는 가상 스크롤로 충족.

### 작업 중 발견·수정
- 소스의 긴 줄이 화면에서 줄바꿈되어 "행 ≠ 소스 줄"이 되면서 미리보기가 앞서 나가던 문제 → 새 소스 줄이 시작되는 행만 모아 수정.
