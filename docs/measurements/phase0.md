# Phase 0 측정 결과

> 측정 장비: Windows 11 PC (x86_64) · 릴리스 빌드 · eframe/egui 0.37.0 · 폰트 직접 구성(맑은 고딕 포함)
> 재현: `cargo xtask gen-samples` 후 `target/release/editor-spike.exe --perf-bench`

## P0-06 대용량 텍스트 — 방식 A (`TextEdit` + `String`)

창 없이 egui를 돌려 **레이아웃 + 테셀레이션 CPU 시간**을 잰 값이다 (GPU 그리기 제외). 입력은 문서 중간에 한글 1글자씩.

| 샘플 | 하이라이트 | 열기(읽기+UTF-8) | 첫 프레임 | 입력 프레임 평균 / 최대 | 유휴 프레임 |
| :--- | :---: | ---: | ---: | ---: | ---: |
| 1MB (1만 줄) | 끔 | 1.4 ms | 387 ms | 7.9 / 8.8 ms | 1.9 ms |
| 1MB | 켬(100개) | 1.4 ms | 390 ms | 7.9 / 8.6 ms | 1.7 ms |
| 5MB (5만 줄) | 끔 | 6.9 ms | 2.3 s | 51.8 / 53.2 ms | 11.6 ms |
| 5MB | 켬 | 6.9 ms | 2.7 s | 57.4 / 60.9 ms | 14.6 ms |
| 10MB (10만 줄) | 끔 | 18 ms | 5.5 s | 114 / 119 ms | 27.0 ms |
| 10MB | 켬 | 18 ms | 5.5 s | 128 / 137 ms | 27.6 ms |
| 50MB (50만 줄) | 끔 | 95 ms | 46.6 s | 738 / 796 ms | 178 ms |
| 50MB | 켬 | 95 ms | 40.7 s | 721 / 757 ms | 148 ms |

### 해석
- 비용은 하이라이트가 아니라 **문서 전체를 매 입력마다 다시 레이아웃하는 `TextEdit` 구조**에서 나온다 (하이라이트 켬/끔 차이 작음).
- 입력 지연은 크기에 거의 비례(약 10ms/MB): **60fps(16ms)를 지키는 한계는 약 1.5MB**, 5MB부터 체감 지연, 10MB 이상은 사실상 편집 곤란.
- 첫 레이아웃(파일을 연 뒤 첫 화면)이 1MB에서도 약 0.4초, 5MB 2초 이상 — 파일 열기 체감에 직접 영향.
- 유휴 프레임도 크기에 비례(10MB 27ms) — 커서 깜빡임·마우스 이동만으로도 CPU를 쓴다.
- **사용자 체감 (2026-10-20)**: 1MB까지 괜찮음, 그 이상은 지연 체감, 10MB 이후 실질적으로 사용 곤란 — 측정과 일치.
- 결론(잠정): PLAN.md §3.6의 "방식 A 잠정 한계 10MB"는 **성립하지 않는다.** 방식 A로 가면 편집 한계를 약 1~2MB로 낮춰야 하고, 그 이상(로그 파일 등)을 편집하려면 방식 B(자체 위젯 + 보이는 줄만 레이아웃)가 필요하다 → P0-10 ADR 0001에서 결정.

## P0-07 메모리·기동 시간 — 렌더러 × 한글 폰트 × 문서

> 재현: `cargo xtask gen-samples` 후 `cargo xtask measure --runs 10` (빈 문서 10회, 10MB 3회 평균)
> 첫 프레임: 프로세스 시작 → 첫 프레임이 화면에 나간 시점(warm). 메모리: 첫 프레임 1.5초 뒤 Windows Working Set.
> 실행 파일 크기: 13.89MB (glow + wgpu 둘 다 포함, LTO thin + strip)

| 렌더러 | 한글 폰트 | 문서 | 첫 프레임 ms 평균 (최소~최대) | 메모리 MB 평균 (최소~최대) |
| :--- | :--- | :--- | ---: | ---: |
| wgpu | 직접 구성 | 빈 문서 | 462 (416~538) | 319 (318~321) |
| wgpu | 없음 | 빈 문서 | 412 (374~510) | 318 (316~319) |
| **glow** | **직접 구성** | **빈 문서** | **362 (314~443)** | **112 (111~117)** |
| glow | 없음 | 빈 문서 | 376 (315~482) | 110 (109~111) |
| wgpu | 직접 구성 | 10MB | 5,056 | 2,153 |
| wgpu | 없음 | 10MB | 2,656 | 2,144 |
| glow | 직접 구성 | 10MB | 5,395 | 1,938 |
| glow | 없음 | 10MB | 2,517 | 1,941 |

### 해석
- **렌더러**: glow가 wgpu보다 메모리를 약 **200MB 적게** 쓴다 (112 vs 319MB). 기동 시간도 비슷하거나 조금 빠르다 → **glow 권장**.
- **한글 폰트(직접 구성)**: 메모리 영향은 약 +2MB로 거의 없다 (memory-map). 빈 문서 기동 시간 차이도 측정 오차 수준.
- **§1.3 잠정 목표 대비**: 빈 문서 메모리 ≤60MB는 glow로도 미달(112MB, 그래픽 드라이버 몫이 큼), warm 기동 ≤300ms도 미달(약 360ms). 목표 수치는 P0-10에서 측정 기반으로 재설정 필요.
- **10MB 문서 = 약 2GB 메모리**: 방식 A(`TextEdit`)는 문서 전체의 글리프 배치를 메모리에 들고 있어 크기에 비례해 폭증한다 (§1.3 목표 ≤150MB 대비 13배). P0-06의 입력 지연과 함께 **방식 B(보이는 줄만 레이아웃)가 필요하다는 강한 근거**.
- 10MB 첫 프레임이 한글 폰트 有 5초 / 無 2.5초로 차이 나는 것은 한글 글리프 레이아웃 비용(폰트 없으면 대체 문자로 처리)이다 — 방식 B에서는 보이는 부분만 배치하므로 사라질 문제.
